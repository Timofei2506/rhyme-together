# RHYME TOGETHER — сетевое кооперативное караоке на двоих

Два игрока на разных устройствах и в разных городах поют **разные партии одной песни**
одновременно, слышат друг друга по WebRTC и получают **общий командный результат**.
Приложение не соревновательное: итог считается как средний уровень дуэта, а не «кто лучше».

**Рабочая сборка:** `npm start` → <http://localhost:3000>

---

**Документация:** [`docs/TZ-MAPPING.md`](docs/TZ-MAPPING.md) — построчное соответствие ТЗ,

## 🎮 Играть вдвоём прямо сейчас (без карты и регистрации)

```bash
bash tools/serve.sh
```

Скрипт поднимает игровой сервер и HTTPS-туннель Cloudflare, затем печатает ссылку
вида `https://xxxx.trycloudflare.com`. Её можно отправить второму игроку — голос
пойдёт по WebRTC (P2P), события — по WebSocket через тот же адрес.

Требования: Android — Chrome, Windows — Chrome/Edge (микрофон доступен только по HTTPS).

Если нужен постоянный адрес — `render.yaml` (Blueprint) или `Dockerfile` на любом
хостинге с WebSocket; в панели хостинга задайте `TURN_URL/TURN_USERNAME/TURN_CREDENTIAL`.

## Архитектура

```
┌───────────── Устройство игрока A ─────────────┐        ┌───────────── Устройство игрока B ─────────────┐
│ экран / UI                                   │        │                                              │
│  ├ Web Audio: инструментал + гайд-вокал       │        │  то же зеркально, партия B                    │
│  ├ Анализ микрофона (pitch FFT/ACF + онсеты)  │        │                                              │
│  └ WebRTC (голос) ─────────────┐              │        │   ┌──────────── WebRTC (голос)               │
└───────────────┬────────────────┼──────────────┘        └───┼──────────────┬───────────────────────────┘
                │ WebSocket      │ голос: P2P (STUN/TURN)     │ WebSocket    │
                ▼                ▼                            ▼              ▼
        ┌────────────────────────────────────────────────────────────────────────┐
        │  Node.js + ws: комнаты, коды, выбор песни, партии,                     │
        │  серверное время, назначение старта, дрейф, сигналинг, командный итог  │
        └───────────────────────────────┬────────────────────────────────────────┘
                                        ▼
                          хранилище статистики (JSON → PostgreSQL/Supabase)
```

**Ключевые принципы**

1. **Сервер — единственный авторитет.** Песню выбирает и партии назначает сервер.
   Старт объявляется абсолютным временем сервера (`startAt`), а не «нажатием кнопки».
2. **Звук не ходит через сервер.** Голос — прямой WebRTC-канал; микрофонный звук для
   оценки не покидает устройство. На сервер уходят только числа: баллы и таймстемпы атак.
3. **Стемы не скачиваются, а синтезируются** из партитуры (Web Audio): нулевая задержка
   загрузки, нет проблем с правами, одинаковый звук у обоих игроков.

### Синхронизация: как именно

1. Клиент 9 раз обменивается `time`/`t0,t1` с сервером, считает
   `offset = t1 − (t0 + RTT/2)` и берёт замер с **минимальным RTT**.
2. Когда оба игрока готовы, сервер выбирает песню и объявляет
   `startAt = now() + lead`, где `lead = max(7000, макс. задержка игрока + 4500 мс)`.
3. Клиент планирует старт в шкале `AudioContext`:
   `ctxStart = ctx.currentTime + (startAt − serverNow()) / 1000`
   и запускает все стемы одним `start(ctxStart, offset)` — начало совпадает у обоих.
4. Во время пения `tick()` каждую секунду сравнивает «где должны быть» и «где играем»:
   – `|Δ| ≤ 700 мс` → подтяжка скоростью в пределах ±5 % (на слух незаметно);
   – `|Δ| > 700 мс` → жёсткий `seek` к серверной позиции.
   Дрейф виден на экране игрока и партнёра.

### Оценка: как именно (без фиктивных чисел)

| Метрика | Вес | Метод |
|---|---|---|
| Ноты | 50 % | автокорреляционный детектор высоты, защита от октавной ошибки; по каждой ноте — медианное отклонение в центах, доля кадров «в ноту» (±60 ¢) и покрытие длительности |
| Ритм | 30 % | детектор атак по оконному минимуму энергии (устойчив к легато), сравнение с сеткой партитуры в окне ±300 мс |
| Синхронность | 20 % | у каждого игрока — свои отклонения атак от партитуры; сравнивается **разница отклонений** с партнёром. Оба поют «чуть позже доли» — дуэт всё равно синхронен |

Командный балл = `0.5·ноты + 0.3·ритм + 0.2·синхронность` (средние по обоим игрокам).
Если метрика объективно недоступна (например, партнёр не дошёл до совместных фраз),
она не обнуляет результат, а вес перераспределяется — и это видно в блоке «Как это считалось».

## Быстрый старт

```bash
npm install
npm start                 # http://localhost:3000
```

Откройте страницу на двух устройствах (или в двух окнах), создайте комнату,
введите код на втором устройстве, включите микрофоны, нажмите «готов» у обоих.

> **Важно:** микрофон и WebRTC работают только в `https://` или на `localhost`.
> Для игры через интернет нужен HTTPS (см. «Деплой») и, желательно, TURN.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `PORT` | порт (по умолчанию 3000) |
| `TURN_URL` | `turn:host:3478?transport=udp,turns:host:5349` |
| `TURN_USERNAME`, `TURN_CREDENTIAL` | доступ к TURN |
| `FORCE_RELAY=1` | принудительно через TURN (диагностика) |
| `RT_DB` | путь к файлу статистики |
| `RHYME_TOGETHER_DEBUG=1` | отладочные хуки (эмуляция обрыва связи для тестов) |

## Тесты

### E2E: два игрока, два браузера, реальный WebRTC

```bash
npx playwright install chromium      # один раз
npm run test:e2e                     # быстрый прогон (сдаёт результат досрочно)
RT_FULL=1 RT_SONG=scarborough npm run test:e2e   # полное исполнение песни
```

Проверяется 28 пунктов, в том числе:

* комнату создаёт игрок 1, по коду входит игрок 2, партии **A** и **B** разные;
* WebRTC-соединение переходит в `connected` (голосовой канал живой);
* сервер назначает `startAt`, обе стороны получили **одну и ту же песню**;
* фактический дрейф воспроизведения — единицы миллисекунд;
* **честность оценки:** «тишина» → 0 баллов, «эталонная мелодия» → 96, «пение на 4 полутона мимо» → 18,
  полное живое исполнение через микрофон → **90.2** при синхронности 96.3;
* балл соответствует формуле 50/30/20;
* обрыв связи → клиент замечает, переподключается и **восстанавливает ту же комнату и партию**.

### Юнит-проверки аудио

```bash
node --input-type=module -e "..."   # см. tools/test-audio.js
npm run test:audio                  # проверки песен и детектора высоты
```

### Музыкальная библиотека

| Песня | Размер | BPM | Партии | Правовой статус |
|---|---|---|---|---|
| Калинка | 4/4, 40 тактов | 120 | Мелодия / Подголосок | общественное достояние |
| Во поле берёза стояла | 4/4, 20 тактов | 84 | Запев / Отклик | общественное достояние |
| Amazing Grace | 3/4, 24 такта | 76 | Melody / Harmony | общественное достояние |
| Scarborough Fair | 3/4, 21 такт | 76→96 | Верхний / Нижний голос | общественное достояние |

Генератор `npm run songs` проверяет, что в каждой партии слоги совпадают с нотами,
ноты не выходят за такт и строки не перекрываются, — «неподготовленных» песен в игре быть не может.

### Как добавить свою песню

1. Положите инструментал и два стема в `src/data/songs/<id>/` (mp3/ogg).
2. Опишите партитуру в `tools/gen-songs.py` (или сразу в JSON): такты, аккорды,
   для каждой партии — `bar`, `beat`, слоги, MIDI-ноты и длительности.
3. Запустите `npm run songs` — генератор не пропустит разметку с перекрытиями.

Формат уже описан так, что стемы можно не синтезировать, а подгружать файлами:
`MusicClock` принимает любые `AudioBuffer`, отличаются только источники.

## Деплой в интернет

### Вариант A: Vercel (статика + API) — ограничение

Vercel serverless **не держит постоянные WebSocket-соединения**. Фронтенд разворачивается
как есть (`vercel.json` в корне), а игровой сервер нужно разместить на хостинге с
долгоживущими процессами (Railway, Render, Fly.io, VPS) и указать его адрес фронтенду.

### Вариант B: один процесс на VPS/Railway/Render (рекомендуется)

```bash
PORT=3000 TURN_URL=turn:... TURN_USERNAME=... TURN_CREDENTIAL=... node server/index.js
```
Поставьте reverse-proxy с HTTPS (Caddy/Nginx) — микрофон требует защищённого контекста.

### База данных

Сейчас — `server/store.js` (JSON, атомарная запись). Интерфейс
`init / touchPlayer / recordResult / leaderboard / profile / stats` совпадает
с таблицами `rhyme_players` и `rhyme_matches`; замена на PostgreSQL/Supabase —
это подмена одного файла (миграция приведена в `docs/schema.sql`).

## Известные ограничения MVP

* Голос за симметричным NAT без TURN может не установиться — задайте `TURN_URL`.
* Библиотека — 4 общедоступные мелодии; добавляются через генератор партитур.
* Статистика хранится в файле, а не в PostgreSQL (адаптер готов к замене).
* Нативный Android/Windows-клиент не собирался: архитектура веб-ориентированная
  (PWA-ready), приложение работает в браузере любого устройства.
