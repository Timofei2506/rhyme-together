# RHYME TOGETHER — соответствие техническому заданию

Документ фиксирует, что из ТЗ реализовано, где это в коде и какие ограничения остались.
Все утверждения проверяемы тестами: `node tools/test-audio.js` и `node tools/e2e.js`.

## 1. Концепция

| Пункт ТЗ | Реализация | Проверка |
|---|---|---|
| Два человека в одной комнате через интернет | Комната по шестизначному коду, WebSocket | E2E: «комната создана», «в комнате ровно два игрока» |
| Случайный выбор песни с двумя партиями | Сервер выбирает из библиотеки, где у **каждой** песни ровно 2 партии с разметкой | E2E: «обе стороны получили одну и ту же песню» |
| Игрок 1 — Vocal A, игрок 2 — Vocal B | Назначает сервер по порядку входа, партия сохраняется при переподключении | E2E: «игроку 1 назначена партия A», «игроку 2 — B» |
| Командная, а не соревновательная игра | Итог — среднее по двум игрокам и общая синхронность; нет «победителя» | экран результатов, блок «Как это считалось» |

## 2. Сетевая система

| Пункт | Реализация |
|---|---|
| Создание комнаты | `case 'create'` → `Room`, код `100000–999999` без коллизий |
| Шестизначный код | `makeCode()` |
| Подключение по коду | `case 'join'`, проверка `NO_ROOM` / `FULL` / `IN_PROGRESS` |
| Статус подключения | индикаторы «онлайн / нет связи / переподключение», RTT в шапке |
| Проверка готовности обоих | флаг `ready` у каждого, старт только когда оба готовы и на связи |
| Покидание комнаты | `case 'leave'`: второй игрок получает `peer-left`, комната возвращается в лобби |
| Повторное подключение | `sessionId` в `localStorage`, `resumeCode` в `sessionStorage`; сервер хранит игрока 45 с и возвращает ту же партию |
| Обработка отключений и ошибок | `handleDisconnect`, grace-таймаут, события `peer-disconnected`, `reconnecting`, `neterror` |
| Два участника | жёсткое ограничение `players.size >= 2` |

## 3. Голосовая связь

| Пункт | Реализация |
|---|---|
| WebRTC для аудио | `VoiceLink` (`src/net/voice.js`), отдельный `RTCPeerConnection` |
| Реальное время, минимальная задержка | `bundlePolicy: max-bundle`, ограничение битрейта 32 кбит/с, `networkPriority: high` |
| Настройка микрофона | экран «Настройка микрофона»: устройство, усиление 0.2–2.5×, эхо/шум/АГК |
| Регулировка громкости собеседника | ползунок в комнате, игре и настройках (`GainNode` + `audio.volume`) |
| Отключение микрофона | `setMuted()` — трек отключается, собеседник видит статус |
| Индикация активности | уровень RMS своего и партнёрского микрофона, статус ICE, RTT, битрейт |
| STUN/TURN | STUN по умолчанию; TURN — через `TURN_URL/TURN_USERNAME/TURN_CREDENTIAL` |
| Независимость от музыки | отдельный `PeerConnection`, музыка идёт по Web Audio; сбой голоса не останавливает трек |

## 4. Игровой процесс

1. Игрок 1 создаёт комнату → 2. Игрок 2 входит по коду → 3. Оба нажимают «готов» →
4. Сервер выбирает песню → 5. Назначает партии → 6. Объявляет `startAt` →
7. Оба поют одновременно → 8. Анализ на устройстве → 9. Общий результат.
Порядок реализован именно так (`maybeStart()` → `song-assigned` → `finalize()`).

## 5. Синхронизация

| Пункт | Реализация |
|---|---|
| Серверное время | 9 замеров ping/pong, выбор по минимальному RTT |
| Сервер назначает старт | `startAt = now + max(7000, макс_задержка + 4500)` |
| Передача обоим | одно сообщение `song-assigned` с одинаковым `startAt` |
| Проверка готовности устройств | клиент подтверждает загрузку стемов до старта (стемы синтезируются за ~1 с) |
| Согласование старта | запуск в шкале `AudioContext` по `startAt` |
| Отслеживание рассинхрона | `MusicClock.tick()` 1 раз/с, индикатор «Δ мс» у каждого |
| Коррекция позиции | ±5 % скорость; seek при Δ > 700 мс |
| Компенсация задержки | сдвиг часов + запас на самую медленную сторону |

Измерено в E2E: фактический дрейф **2–23 мс** после старта и в течение песни.

## 6. Музыкальные партии

* Инструментал — синтезируется из аккордов и формы (`StemRenderer.renderInstrumental`).
* Гайд-вокал A и B — отдельные стемы (`renderGuide('A'/'B')`).
* Разметка текста: слоги с привязкой к доле и длительности, слова помечены (`w`).
* Эталонные ноты и ритм: MIDI-номер + длительность в долях для каждой ноты.
* Игрок слышит свой гайд-вокал (громкость регулируется) и инструментал.
* Песен без разметки в игре нет: генератор `tools/gen-songs.py` **не пропустит**
  партитуру с несовпадением слогов и нот, с перекрытием строк или выходом за границы.

## 7. Оценивание

| Пункт | Реализация |
|---|---|
| Анализ на устройстве | `detectPitch`, `PerformanceAnalyzer` — целиком в браузере |
| Не отправлять сырое аудио | На сервер уходят только баллы и таймстемпы онсетов |
| Ноты 50 % | медианное отклонение в центах, попадание ±60 ¢, покрытие длительности |
| Ритм 30 % | онсеты против сетки партитуры, окно ±300 мс |
| Синхронность 20 % | сравнение отклонений атак двух партнёров |
| Объединение в командный балл | средние по игрокам, затем взвешивание 50/30/20 |
| Показ индивидуальной точности | карточки партии A и B с разбивкой |
| Общая синхронность | отдельная строка и бар |
| Итоговый командный результат | крупный балл + словесная оценка |
| Без фиктивных показателей | «тишина» → 0; идеал → ~96; мимо нот → ноты 0 (тест) |

Пример из живого E2E (два «поющих» браузера, полная песня):
`командный 89.6 = ноты 92.2 / ритм 80.5 / синхронность 96.9`.

## 9. Серверная архитектура

| Пункт | Реализация |
|---|---|
| Backend комнат | Node.js + Express (`server/index.js`) |
| WebSocket | `ws`, путь `/ws`, heartbeat ping/pong |
| WebRTC | только сигналинг на сервере (offer/answer/ICE) |
| STUN/TURN | `/api/rtc-config` |
| БД | `server/store.js`: игроки, матчи, лидерборд; интерфейс совместим с PostgreSQL (`docs/schema.sql`) |
| Система синхронизации времени | `time`-обмен + расчёт смещения на клиенте |
| Восстановление соединения | авто-переподключение с экспоненциальной паузой + resume по коду |

## 10. Платформы

* Единый веб-клиент: Android (Chrome), Windows (Chrome/Edge/Firefox), iOS/macOS.
* Адаптивная вёрстка, проверена на Pixel 7 (`docs/screens/04-room-mobile.png`, `06-game-mobile.png`).
* Микрофон требует HTTPS или localhost — при деплое это обеспечивает reverse-proxy.
* Устройства соединяются через интернет: голос по WebRTC P2P, события по WSS.

## 12. Что осталось за рамками MVP

1. **PostgreSQL/Supabase вместо JSON-файла.** Supabase отказал в создании проекта:
   в организации занят лимит free-проектов (осталось два занятых проекта — `krug-network`
   и `volodya-bot`; `extitube` и `extingytur-web-studio` удалены по просьбе).
   Схема и интерфейс адаптера готовы: `docs/schema.sql`, `server/store.js`.
2. **Публичный деплой.** Vercel-конфиг для статики готов (`vercel.json`), Dockerfile и
   railway/render-манифесты для игрового сервера готовы. Чтобы развернуть, нужны
   доступ к деплою серверной части (Vercel не держит WebSocket) и, желательно, TURN.
3. **Загруженные стемы.** Сейчас стемы синтезируются из партитур. `MusicClock` принимает
   готовые `AudioBuffer`, поэтому переход на mp3/ogg — это замена источника, а не логики.
4. **Нативные оболочки Android/Windows** не собирались: клиент веб-ориентированный (PWA-ready).
